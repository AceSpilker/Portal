Portal 二期迁移方案 · Django × Art Design Pro

在 phase2/ 全新工程中重写后端（FastAPI → Django 5.2 LTS + Django Ninja + Channels）与前端（Art Design Pro v3.0.2），功能与一期 1:1 对齐（feature-spec 220 功能点基线不变）。一期（FastAPI + v1 前端）全程冻结运行、零改动，二期验收后切换为双容器部署——nginx 容器托管前端（/portal/ 二级路径）+ Django 后端容器（端口不发布到宿主，仅容器网络通信），卷内数据直接沿用。本方案覆盖选型、工程结构、契约、数据迁移、认证、WebSocket、后台任务、前端、部署、测试与阶段计划全部细节。

方案版本 v1.0 2026-10-21 后端 Django 5.2 LTS + Ninja 前端 Art Design Pro v3.0.2 一期零改动 · 数据沿用 双容器：nginx 前端 /portal/ + 后端端口不暴露

1目标、范围与路线变化

1.1 二期定义

  • 新工程：项目根新建 phase2/（含 doc/、backend/、frontend/），与一期目录完全隔离，互不干扰。
  • 后端重写：FastAPI（Python 3.12）→ Django 5.2 LTS（同为 Python 3.12），API 层用 Django Ninja，WebSocket 用 Channels。
  • 前端建设：Art Design Pro v3.0.2（已拉取于 frontend-artdesign/，D0 阶段迁入 phase2/frontend/）。
  • 功能不变：285 个 API 端点、4 条 WebSocket、17 项后台任务、32 张表、220 个功能点（feature-spec v1.6 基线）、传输加密、i18n、PWA——全部 1:1 保留，只换实现载体。
  • 数据不变：SQLite 主库、data/ 卷资产（RSA 密钥、图标、采样数据）直接沿用，切换日零数据迁移。

6数据模型与数据迁移

6.1 32 表 → Django 模型六步法（零数据迁移）

一期 23 个模型文件（app/models/：user/portal/probe/monitor/port/lan/network/flow/ai/knowledge/notify/audit/setting/sync/tools/tunnel/schedule/layout/api_token/agent/system_log/base）对应 SQLite data.db 约 32 张表。策略：Django 模型对齐既有库，库不动模型动。

  1. 快照：复制生产 data.db 为开发基线（并行期二期只连快照副本，见 6.3）。
  2. inspectdb：python manage.py inspectdb > apps/_snapshot_models.py 生成全部表的模型草案（自动带 db_table/db_column/managed=False）。
  3. 清洗归位：按 §4 的 app 划分拆进各 models.py；managed=False 改 True（获得后续迁移能力）；修正类型（TEXT JSON 字段按一期用法选 JSONField/TextField）；User 表接入 AUTH_USER_MODEL（AbstractBaseUser，username 主键语义不变，password 字段存 bcrypt 串）。
  4. 生成迁移：makemigrations 生成 0001_initial——此时迁移 DDL 应与既有表结构一致。
  5. fake 接管：对快照库 migrate --fake-initial（Django 检测到表已存在则只记录迁移记录，不动数据）。
  6. schema diff 校验：写脚本对一期 SQLAlchemy metadata 与二期 Django migration 状态做逐表逐列 diff（名/类型/nullable/索引/唯一约束），D1 关卡要求 diff 为空；32 表逐表 count(*) 与抽样行比对。
⚠️ SQLite 注意：一期若建了 WITHOUT ROWID/部分索引等 Django 迁移不还原的细节，diff 脚本会暴露；此类差异保持 managed=False 单表豁免（Django 完全可用非托管表），不追求 100% 托管。

6.2 密码哈希兼容（登录无缝）

一期用 bcrypt（passlib 风格裸串 $2b$12$... 直接存列），Django 内置 bcrypt hasher 期望 bcrypt$<hash> 前缀格式。方案：写一个自定义 hasher 挂 PASSWORD_HASHERS 首位：

# apps/accounts/hashers.py —— 识别一期裸 bcrypt 串，登录验证直通
class PortalLegacyBcryptHasher(BasePasswordHasher):
    algorithm = "portal_bcrypt"          # identify(): 串以 $2b$/$2a$/$2y$ 开头即认领
    def verify(self, password, encoded): return bcrypt.checkpw(...)
    def encode(...) / needs_update(...)   # 验证通过后标记升级为 Django bcrypt$ 格式（可选）

登录端点不依赖 Django authenticate 也可（沿用一期 security.py 的 bcrypt 直查——更省事，推荐，hasher 仅作为未来用 Django 密码体系的兼容垫片备着）。效果：既有用户密码零重置、切换日无感。

11.2 nginx 配置（deploy/nginx/nginx.conf 核心段）

server {
  listen 80;
  client_max_body_size 8m;                      # 图标上传 ≤2MB + 文件上传余量

  # —— 前端：二级路径 /portal/ ——
  location /portal/ {
    root  /usr/share/nginx/html;                # dist 已拷至 .../html/portal/
    try_files $uri $uri/ /portal/index.html;    # SPA 深链接回退
  }
  location = / { return 302 /portal/; }         # 根路径跳转门户（可选）

  # PWA：入口与 SW 禁缓存（autoUpdate 依赖）
  location = /portal/index.html { add_header Cache-Control "no-cache"; }
  location = /portal/sw.js      { add_header Cache-Control "no-cache"; }

  # —— 后端反代（docker 内网 backend:8000，端口不暴露宿主）——
  location /api/    { proxy_pass http://backend:8000; }
  location /icons/  { proxy_pass http://backend:8000; }
  location /tunnel/ { proxy_pass http://backend:8000; }   # SSH 隧道反代
  location /files/  { proxy_pass http://backend:8000; }
  location /ws/ {                                          # 4 条 WebSocket
    proxy_pass http://backend:8000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;                  # ssh-terminal / ai-chat 长会话
  }
}
⚠️ WS 反代三个必要件：proxy_http_version 1.1 + Upgrade/Connection 头 + 足够长的 proxy_read_timeout——缺任一项都会造成 WebSSH 终端秒断或 AI 流式中止，是 D9 冒烟的必测项。

R4Channels/InMemory 层与一期 wsbus 行为差异（广播时序/断连）中消费者逐条对照一期实现；四消费者专用测试；前端断线退避逻辑不变，端到端联调覆盖
R532 表 inspectdb 差异（类型/索引/约束还原不全）中六步法含强制 schema diff 清零关卡；个别难还原表保持 managed=False 豁免；切流前卷备份兜底
R6依赖版本陷阱（cryptography ≥45 的 aarch64 SIGILL 等）中requirements 约束与注释整体照搬一期；Docker 镜像内冒烟（握手/加密回环）作为 D0/D9 关卡
R7切流日数据/行为不一致中停机窗口 + 卷备份 + 分钟级回滚到一期镜像（§11.2）；切流前用生产快照做全量验收（F7 在快照上执行）
R8工期（后端近乎重写 API 层 + 30 服务 DB 改写）高分域推进（D3–D7 每域可独立验收）；一期持续在线无交付压力；schemas/services 最大复用把重写面压缩到"路由声明 + ORM 调用"两层
R9二级路径 /portal/ 引发的路径问题（静态资源 404 / 路由 base / SW scope / 深链接）中Vite base 与 router base 同源配置（import.meta.env.BASE_URL）；dev 亦带前缀消除环境差异；API 走根绝对路径 /api 不受影响；D9 冒烟必测深链接刷新与 SW 更新
R10nginx WS 反代配置不当（缺 Upgrade 头 / 超时过短）致 WebSSH 与 AI 流式断连中§11.2 标准配置段（http 1.1 + Upgrade + read_timeout 3600s）；D5/D6/D9 关卡各含对应 WS 实测
