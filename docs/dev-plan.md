# Portal · 开发计划与技术清单（Dev Plan）

> **版本**：v1.3 ｜ **日期**：2026-09-02 ｜ **关联文档**：《功能详述 feature-spec》v1.6、《总体设计方案 design-proposal》v0.7、《接口详述 api-spec》v1.2
>
> **v1.1 变更**：数据库策略调整——**SQLite 为运行主库，定时镜像推送到 NAS 上的 MySQL**（灾备/集中存储）；新增 **P23 · MySQL 数据同步** 阶段（5 步），技术清单补充 MySQL 驱动；总步骤 103 → 108。
>
> **v1.2 变更**：新增 **P24 · 传输加密（全链路密文化）** 阶段并已完成（应用层 RSA+AES-GCM 信封，HTTP 下数据不明文传输）；总步骤 108 → 113。
>
> **v1.3 变更**：**外部存储与缓存体系设计定稿**——客户机已有的 MySQL / Redis 服务只需在本系统配置即可使用，未配置时全部回退 SQLite + 进程内存。① P23「MySQL 数据同步」细化为 6 步（连接管理与配置页分离、密码加密存储、健康自检接入单列）；② 新增 **P25 · Redis 缓存与会话** 阶段（4 步：连接管理与配置页、会话存储接入、缓存基础设施、健康自检与降级）；技术清单补充 redis-py。总步骤 113 → 118，阶段 25 → 26。
>
> **文档定位**：本文档是**开发执行的唯一依据**——技术工具清单、测试策略、以及把全部业务功能拆解为"阶段（Phase）→ 步骤（Step）"的执行清单。每个步骤带完成状态，开发时按步骤推进、实时更新状态；**每个阶段结束必须通过单元测试与业务功能测试两道关卡**才算完成。

**状态图例**：⬜ 未开始 ｜ 🔄 进行中 ｜ ✅ 已完成（须通过该阶段两道测试关卡）｜ ⛔ 阻塞

**规模总览**：**26 个开发阶段 · 118 个步骤**，分布在三个里程碑（M1 MVP / M2 增强 / M3 进阶）。当前进度：**41 / 118**（P0、P1、P2、P4、P24 完成；P7.1 设置框架提前落地；P3 八步完成，待真实双环境验收）。

## 2. 测试策略总则

1. **单元测试**：
   - 后端 pytest，覆盖 `services` 与 `core` 层核心逻辑（环境解析、探活判定、采集换算、告警状态机、JWT/密码、Flow 表达式沙箱、通知路由）；
   - 前端 Vitest，覆盖 stores、搜索过滤、布局序列化、工具函数。
2. **接口测试**：FastAPI TestClient + httpx AsyncClient，连接临时 SQLite（内存库），覆盖 API 契约与权限（401/403）。
3. **业务功能测试**：以《功能详述》的**功能点编号**（如 M04-10）为验收单元，每阶段列出手工测试清单，逐条执行勾验；关键链路在 M1 末补 Playwright 自动化。
4. **覆盖率门禁**：后端核心 services ≥ 80%、全局 ≥ 70%；不达标不得关闭阶段。
5. **状态更新约定**：完成一个步骤 → 本文档状态 ⬜→✅ 并在 `logs/` 记一笔；阶段内步骤全 ✅ 且两道测试关卡通过 → 阶段标记 ✅；被外部问题卡住 → ⛔ 并注明原因。

## 5. 执行约定

1. **顺序执行**：按 P0 → P22 顺序推进，允许同里程碑内无依赖的阶段并行（如 P9 通知中心可提前）；
2. **状态即真相**：本文件的步骤状态就是开发进度，完成一步改一步，不写"记忆里的进度"；
3. **阶段门禁**：每阶段"单元测试关卡 + 业务功能测试关卡"全部通过，阶段才能标 ✅；未通过则停在 🔄 并记录阻塞原因；
4. **日志联动**：每关闭一个阶段，在 `logs/` 写验收日志（测试结果、发现的问题、覆盖率数据）；
5. **需求变更**：评审中新增强功能点 → 先更新 `feature-spec`（升版本），再同步到本计划对应阶段。
