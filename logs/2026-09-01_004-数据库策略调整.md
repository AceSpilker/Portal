## 需求（用户原意）

数据库可以使用 MySQL，NAS 上有 MySQL；最好先使用 SQLite，然后定时往 MySQL 上推送。

## 完成情况

确定**双库数据策略**并落实到两份文档：

1. **策略定稿**：
   - **SQLite = 运行主库**（`/app/data/portal.db`）：全部业务读写走它，零依赖、低延迟，系统不依赖 MySQL 可用性；
   - **MySQL = 灾备与集中存储**（NAS 上已有实例）：定时把业务数据镜像推送到 MySQL，间隔可配；
   - MySQL 不可达不影响本地任何功能，恢复后自动补推；支持"立即推送"与"从 MySQL 恢复到 SQLite"；
   - 敏感表（会话/Token）不同步；新增 `sync_state` 表记录每表最近推送时间/行数/结果。
2. **feature-spec v1.2**：M15 系统设置新增功能点 **M15-12 MySQL 数据同步**（12 项），规模总览 220 → 221；阶段规划与新增清单同步。
3. **dev-plan v1.1**：
   - 新增阶段 **P23 · MySQL 数据同步（SQLite→MySQL）**，5 个步骤：ORM 双库兼容验证 → 同步配置与连接测试 → 镜像推送引擎（upsert + 删除对齐）→ 状态与失败重试 → 灾难恢复；附单测/业务测试两道关卡（含"停 MySQL 容器本地照常、恢复后补推"验证）与退出标准（真实 NAS MySQL 连续 72h 推送无失败）；

   - 步骤总数 103 → 108，进度看板与统计同步。

## 关键决策

1. **主备定位而非迁移**：不是"换数据库"，SQLite 仍是运行时唯一写入点——保证门户在 MySQL 停机/维护时完全可用，符合 NAS 场景；
2. **全量 upsert 镜像而非增量 CDC**：个人门户数据量小，按主键 diff 全量推送简单可靠，删除通过对齐处理，避免引入变更捕获复杂度；
3. **同步范围可配置且默认排除敏感表**：会话、API Token 等不进 MySQL；
4. 推送与恢复均走 APScheduler/手动触发，复用现有任务框架，不引入额外组件。
