## 二、P9 开发

### 9.1 推送渠道(8 类)
- 新模型 `notify_channels`(type/name/config JSON/enabled)+ `notify_rules`(event/channel_ids/enabled/quiet_start/quiet_end),注册建表;
- `services/notify.py`:**payload 构造纯函数**(bark GET 路径编码/telegram sendMessage/webhook JSON{event,source,level,title,body,timestamp}/wecom·dingtalk·feishu 群机器人格式/ntfy Topic+Priority 头/SMTP MIME 构造)+ `send_channel`(httpx 可注入 MockTransport;SMTP 走 smtplib+to_thread,可 monkeypatch);
- 渠道 CRUD `/api/notify-channels…`(M)+ `POST /{id}/test`:**敏感字段(device_key/bot_token/password)回传脱敏为 ******,保存时 ****** 表示保持原值**;
- 零新增依赖(httpx/smtplib 均为现有/标准库)。

### 9.2 站内通知
- `GET /api/notifications` 升级为分页对象 `{items,total,unread}` + level/unread 筛选;新增 `unread-count` 角标、`read-all`、`DELETE /{id}`;旧 P6.4 端点迁移至 `api/v1/notify.py`;
- **WS 事件总线下沉**:probe.py 的连接组移入 `services/wsbus.py`(消除 notify→probe 循环依赖),通知写入后广播 `{"type":"notification",…}`;
- 前端:`api/notify.ts` + `stores/notify.ts`(未读角标/列表/筛选/WS 接入)+ `NotificationCenter.vue`(顶栏铃铛:角标、级别筛选、仅看未读、单条已读、全部已读、删除),probe store 的 onmessage 按 type 转发 notification 事件。

### 9.3 通知规则
- `GET/PUT /api/notify-rules`(PUT 全量保存,事件枚举与 HH:MM 校验);
- `dispatch()`:站内写入 → **聚合去重**(同 dedup_key 300s 窗口合并)→ 路由规则 → **规则级免打扰**(HH:MM 可跨午夜,start==end 视为全天;站内始终写入,免打扰仅抑制外部渠道);
- **探活接入**:probe.apply_result 状态翻转改为调用 dispatch(app_down/app_up 事件),P6.4 事件源正式接入 P9 出口。

### 前端设置面板
`NotifyPanel.vue`(设置 → 通知):渠道卡片(启用开关/测试/编辑/删除)+ 八类渠道动态表单 + 事件×渠道勾选矩阵(渠道列动态生成)+ 每事件免打扰时段;菜单新增「通知」,i18n 中英全套(494=494 key 对称)。

## 关键决策

1. **P9 看板 🔄(3/3)**:退出标准「三种渠道真机收包」需真实 Bark 设备/TG bot/SMTP 凭据,与 P3/P8 同口径;
2. notifications 表沿用 P6.4 已建结构(无 user_id,单管理员家庭场景全局通知),避免无谓迁移;
3. WS 事件总线独立成 wsbus 模块,为后续 P10(metric_alert)、P11(port_*)复用;
4. 契约演进:`GET /notifications` 从数组升级为分页对象——无既有消费者(前端此前未接入),api-spec 已同步。
